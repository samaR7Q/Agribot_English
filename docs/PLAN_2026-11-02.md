**You asked:** a new, separate English Agribot with fewer features. It uses Gemini Live, crop knowledge without RAG, mandi with dummy rates and no weather. It keeps the current no-info handling, intent / topic change / probing, and what-can-I-sow / sowing / harvest timing. The front end matches the screenshot, with the avatar, and has no language switch. Explain Gemini Live and its pricing first, and list what else to consider.

**TL;DR**
- **Gemini Live** is one WebSocket where the farmer's voice goes in and Gemini's voice comes out. There is no separate STT, LLM or TTS. Replies are fast and the farmer can interrupt.
- **Logic:** everything we do today with code steps (intent, topic change, probing) becomes **function calls**. The model calls our backend tools, and the tools enforce the rules (missing district, crop switch, out of scope).
- **Cost:** about **$0.10–0.15 per 3-minute call** (rough estimate, to be measured).
- **Crop info in the prompt:** don't put all of it there. Live bills the **whole context on every turn**, with no caching. Keep a short prompt and fetch a crop's info card through a tool when needed. It's still no RAG, just a lookup from a JSON file.

## 1. What Gemini Live is and how a call would work

**Problem:** we need to pick the model and understand the flow before building.

**What it is**
- A real-time voice API.
  - It keeps a stateful WebSocket open for the whole call.
  - Mic audio streams in: 16 kHz, 16-bit PCM.
  - Gemini's spoken reply streams back: 24 kHz PCM.
- Built in:
  - Voice activity detection: it knows when the farmer stops talking.
  - Barge-in: the farmer can interrupt Bashir.
  - Transcripts of both sides, which we need for History and logs.
  - Function calling.
- **It replaces our whole chain** (Whisper STT → MQG → RAG → Gemma → filler → XTTS). There are no fillers either, because the first audio comes back in well under a second.

**Models** (on Google's pricing page today)

| Model ID | Status | Function calling | Price |
|---|---|---|---|
| `gemini-3.8-live` | current | yes | same table for all three (section 2) |
| `gemini-3.1-flash-live-preview` | preview | **sync only** (the model waits for the tool reply) | same |
| `gemini-2.5-flash-native-audio-preview-12-2025` | older preview | sync + async | audio same, text input $0.50/M |

**Recommendation:** `gemini-3.8-live`. Check it on our key in AI Studio first.

**Call flow (proposed)**
```
Browser (mic + avatar)  ⇄  our FastAPI WebSocket  ⇄  Gemini Live
                                  │
                                  ├─ tools: get_mandi_rate, get_crop_info, get_crop_timing,
                                  │         what_can_i_sow, update_profile, set_current_crop
                                  ├─ session store (profile, current crop, history)
                                  └─ logs (transcripts, tool calls, token usage per turn)
```
- **Server-to-server**, i.e. the browser connects to our backend, not to Google.
  - Reasons: the API key never reaches the browser, the tools run in our backend, and every turn is logged like the current session logs.
  - Google also supports the browser connecting directly with short-lived tokens. It is slightly faster, but then the tools and logs get harder.
- **Greeting:** when the session opens, the backend sends one text turn ("greet the farmer") and Bashir speaks first, like the screenshot.

**Limits to design for**

| Limit | Value | What we do |
|---|---|---|
| Audio session | 15 min without compression | turn on context window compression (sliding window), which removes the limit |
| One connection | ~10 min | session resumption: the handle is valid for 2 h, and the backend reconnects on Google's "GoAway" warning without the farmer noticing |
| Output | audio only per session | transcripts give us the text |

## 2. Pricing

**Problem:** how much does a call cost?

**Paid tier, per 1M tokens** (official pricing page, 2 Nov)

| | Text input | Audio input | Audio output |
|---|---|---|---|
| `gemini-3.8-live` / `3.1-flash-live-preview` | $0.75 | $3.00 (≈ $0.005/min) | $12.00 (≈ $0.018/min) |

- The free tier exists but is rate-limited. On the free tier, Google may use the data to improve its products. **Use the paid tier for real farmers.**
- **The catch:** on every turn Live bills **all tokens in the context** (system prompt + tool definitions + full audio history so far). It has no context caching. Audio piles up at about 25 tokens per second.
- **Rough estimate for a 3-minute call** (8 turns, 4k-token prompt):

| Part | Tokens | Cost |
|---|---|---|
| Prompt + tools re-billed 8× | ~32k text | ~$0.02 |
| Audio history re-billed per turn | ~20k audio | ~$0.06 |
| Bashir's speech | ~3k audio out | ~$0.04 |
| **Total** | | **≈ $0.12 per call (≈ PKR 34)** |

- The same call with all crop info in a **30k-token prompt** costs ≈ **$0.30**. That's why crop info goes through a tool (section 3).
- These are estimates. The prototype will log the real `usageMetadata` per turn, and we'll compare it with the billing console.
- **Cost controls:**
  - a max call length (e.g. 10 min)
  - hang up after silence
  - sliding-window compression
  - a spend cap on the Google project

## 3. Crop knowledge without RAG

**You asked:** no RAG, but keep basic crop info. Is the prompt OK for that, now that we're on Gemini?

**Recommendation: a small prompt plus a lookup tool, not one big prompt.**
- **System prompt (always loaded, ~3–4k tokens):**
  - Bashir's persona
  - the rules
  - the list of supported crops
  - out-of-scope handling
  - short crop facts (1–2 lines per crop)
- **`get_crop_info(crop, topic)` tool:** returns a short card from `data/crops/<crop>.json`.
  - Topics: varieties, land prep, seed rate, fertiliser, irrigation, main pests/diseases, harvest.
  - It is a plain dictionary lookup, with no vectors and no search, so it is still "no RAG".
  - Cost: only the card asked for enters the context.
- **Why not everything in the prompt:**
  - the per-turn billing above
  - the model mixes crops more often when it sees all of them at once
  - it is harder to update one crop
- **Source of the cards:** translate and trim the current KB chunks to English, starting with the 9 calendar crops: wheat, maize, sugarcane, cotton, rice, sesame, canola, berseem, oat.
- **Rule in the prompt:** answer only from the card. If something isn't in the card, say so and don't invent it, especially for pesticide doses.

## 4. Mandi with dummy rates

**You asked:** keep mandi with arbitrary rates for different crops in different areas, and enough of them.

**Proposal**
- **File:** `data/mandi_rates.json`, made by a seeded script so it can be regenerated.
- **Coverage:** ~15 commodities × every district we support (the current `domain/districts.py` list). That's roughly 500–1,000 rows.
- **Each row:** min / max / average in PKR, unit (per 40 kg / maund, per kg for fruit), the mandi name and a date.
- **How the rates are made:** a realistic base price per crop, with a ± 3–8% spread per district so neighbouring districts look different.
- **Tool:** `get_mandi_rate(commodity, district)`.
  - No district in the profile or the question → returns `district_missing` → Bashir asks for the district.
  - No commodity → returns `commodity_missing` → Bashir asks "Which crop's rate do you want?" (the current mandi probe).
  - A district we don't have → returns the nearest mandi and says so.
- **Like today:** mandi never saves or erases the crop in the profile.
- **The data is marked as demo** in the file, and the prompt says "today's rate in X mandi". I'll keep the wording neutral. **Say if you want "these are sample rates" spoken out loud.**

## 5. Core flow: intent, topic change, probing, no-info cases

**You asked:** the same intent classification, the same agri flow with topic change and profile-filling probes, the same no-district / no-crop / no-vegetables handling, and what-can-I-sow / sowing time / harvest time as today.

**How each piece maps**

| Today (pipeline step) | New (Live) | Who decides |
|---|---|---|
| MQG intent: agri / mandi / greeting / small talk / out of scope | the system prompt lists the intents; the model picks one by calling a tool, or answers small talk directly | model, with the backend checking every tool call |
| Topic change ("switch to maize?") | `set_current_crop(crop)`: if it differs from the saved crop, the tool returns `confirm_switch {previous: "wheat"}` → Bashir asks → on "yes" the crop is saved | **backend** (deterministic) |
| Unsaid crop guessed by the classifier (the "ask again" bug) | can't happen in the same way: the model passes the crop the farmer said | — |
| Probing (district, crop, land size, irrigation, animal age …) | each tool returns `missing: [district]` when needed → Bashir asks one question → `update_profile` saves it → the tool is called again | **backend** decides what is missing; the model only asks |
| No district / no crop | same `missing` replies as above | backend |
| Vegetables / unsupported crops | `get_crop_info` returns `unsupported` → fixed reply: "I can help with wheat, maize, … — vegetables aren't covered yet." | backend |
| What can I sow (this month / a named month) | `what_can_i_sow(month?)` → the current `sowing_calendar` in English | backend data |
| Sowing / harvest time, "can I sow X today?" | `get_crop_timing(crop, date?)` → schedule + "yes/no today" + other crops this month (the current crop-timing answer) | backend data |
| Weather | removed: polite "not available in this version" | prompt |
| Filler sentences | not needed (fast first audio) | — |

**Main trade-off, so you can decide knowing it**
- Today intent is a separate, testable step.
- With Live, the model picks the intent itself (by choosing a tool). The rules that matter are still in code, because the tools refuse or ask. But "did it call the right tool" needs its own test set.
- **Plan:**
  - an English query bank (translated from `Query_Bank`)
  - run it in **text mode** over the same session (Live accepts text input), so tests are cheap and repeatable
  - check the tool calls and answers, like the current A/B runs
- **The alternative, if you want the old pipeline's control:** a cascade. Gemini STT → a Gemini Flash text router → a Gemini Flash answer → Gemini TTS. It is closer to today's code, but about 2–4 s slower per reply, has no natural barge-in, and has more parts. **I recommend Live + tools.**

## 8. Other things to consider

- **English accent and voice:** farmers' English with a Pakistani accent. Live's recognition is good, but this needs testing with real recordings. Pick a male voice that fits Bashir and test 2–3 voices.
- **Wrong answers in a voice app are worse than in text.** Keep the "only from the card" rule and log every answer that wasn't backed by a tool call.
- **Pesticide doses:** only from the cards, never from model knowledge.
- **Barge-in on a noisy line:** background noise can cut Bashir off. Tune the VAD sensitivity, or use push-to-talk if testers complain.
- **Session store:** SQLite for profiles and history (no Redis needed at this size).
- **Logs:**
  - per call: transcripts, tool calls with arguments/results, per-turn token usage, cost
  - layout like the current `session_logs_backend`, so the same review scripts work
- **Concurrency/rate limits:** the paid tier limits concurrent Live sessions per project. Check the limit for the expected number of testers.
- **Errors:** if Gemini drops or the network fails mid-call, play a short "connection lost, tap the mic again" and keep the profile.
- **Preview models can be renamed or retired:** keep the model ID in config, not in code.
- **What we lose vs the current bot:**
  - Urdu/Punjabi
  - our own STT/TTS (no on-prem option)
  - the weather API
  - the deep KB with the source of each answer
- **Data:** farmer audio goes to Google. Fine for a demo, but it needs a line in the terms for real users.
